# Dayside 1.0.1：Mac 验收、Developer ID 签名、公证与发布（交给 Codex）

你在一台真实的 Mac 上接手 ninondev/Dayside 的分支 `codex/v1.0.1-handoff`。云端已经做完能在 Linux 上做的工作，
剩下的每一项都必须在 macOS 上实测。请严格按顺序做，每一步都把命令、输出摘要和产物路径记进
`handoff/v1.0.1-mac-acceptance.json`（新建），失败的运行也要原样保留证据（日志、xcresult、崩溃报告），不许删。

**分两段执行。** 用户的 Apple Developer Program 注册（2026-10-08）还在审核中，审核通过前建不了 Developer ID 证书。
- 第一段（现在就做）：第 0–7 步和第 9 步，全部用 ad-hoc 签名的本地构建。做完把结果写进记录、提交推送，然后停下向用户汇报。
- 第二段（用户说审核已通过后再做）：第 8 步（证书、公证凭据、签名、公证、DMG、发布门、新用户账户），
  用正式签名版重做第 4 步和第 5 步的手动 20 次，最后第 10 步。

## 不可违反的规则

1. 内部里程碑 1.0.1，对外版本仍是 1.0（`MARKETING_VERSION = 1.0`，不要改）；构建号 `CURRENT_PROJECT_VERSION` 已在云端从 19 升到 20（工程里 8 处），不要再改。
2. 没有外部用户：不做升级数据迁移。
3. 不放宽任何测试断言与门（2 ms 测速门、发布身份检查、峰值门、无障碍门都不许放宽、跳过或改阈值）。
4. Rust release 配置保持 opt-level 3、thin LTO、codegen-units 1，除非有可比实测证明别的更好。
5. 任何一项验收没过，就不发布安装包、不打 tag。全部通过后，发布前再向用户确认一次。
6. 不提交任何密钥、密码、证书或 notarytool 凭据；凭据只放在登录钥匙串。
7. 提交只推到 `codex/v1.0.1-handoff`；提交信息写清改了什么和为什么。

## 2. 2 ms 测速门（P2）

按原来的方法测：每个 4000 字节夹具 25 个样本，连跑三次，`nice -n 10`，持有共享 CPU 锁。
```bash
mkdir -p backup && cd RustCore
for i in 1 2 3; do nice -n 10 cargo test --locked --release --lib understand::speed_tests::understand_speed_gate \
  -- --ignored --exact --test-threads=1 --nocapture 2>&1 | tee ../backup/speed-gate-$i.log; done
```
- 1.0 基线（Mac，opt 3 + thin LTO）：prose 2.634 ms，hostile 4.728 ms，email 3.515 ms，九次全部失败。
- 云端按 callgrind 指令数折算的预期：见文末「云端数据」。
- 通过标准：三次都通过（三个夹具的中位数都 < 2 ms），并且三个校验和不变。
- 没通过：保留日志，用 Instruments（Time Profiler）找热点，只做输出等价的优化（校验和必须不变），再测。
  不许改门、改夹具、改样本数。

## 6. 内存（README 已知问题第 4 条）

用 `Tools/memory_tour_probe.sh` 量「打开地球窗 → 拖动 → 复制图片 → 关窗 → 等 15 秒」各阶段的 footprint，Debug 与 Release 各一次。
云端只读排查得到的怀疑点（按可能性排序，未经实测）：
1. 复制海报后，`PixelPool` 每种长度最多留 2 块（每块 2400×920×4 ≈ 8.8 MB），`MapRaster.cache` 还留 2 张 1800×690×4 ≈ 5 MB 的海报位图，
   它们要等最后一张地图消失 10 秒后才释放。
2. `sky.rs` 的画布地形网格最多缓存 3 份（每份 3·W·H ≈ 3.7 MB），按份数而不是字节数限额。
3. 释放依赖 `WorldMapView.onDisappear` 把使用计数降到 0（`MapRaster.swift:45-49`）；如果关窗时 SwiftUI 保留了视图树、onDisappear 没触发，
   地形、网格和像素池就一直不释放。先实测确认。
4. `CityIndex.shared` 映射 14.9 MB 的城市索引，从不关闭（文件映射，干净页可回收）。

要求：先测出关窗后不回落的那部分，再针对性修复，修复前后各测一次写进记录；只有实测改善才改 README 第 4 条。

## 8. Developer ID 签名、DMG 与公证（用户已付费开通 Apple Developer Program 并完成实名）

云端已写好并测过流程（`Tools/test_release_sign_notarize.py` 跑 `--dry-run`）：
- `Tools/sign_bundle.sh` 默认仍是 ad-hoc；设置 `MEANTIME_SIGN_IDENTITY="Developer ID Application: <名字> (<TEAMID>)"` 时
  用该身份 + 安全时间戳 + hardened runtime + `TahoeTime-signing-Release.entitlements` 重签（只允许 Release）。
- `Tools/release_sign_notarize.sh <Release 版 Dayside.app> <arm64|x86_64> [--profile dayside-notary] [--out 目录]`：
  重签 → 验签（TeamIdentifier、Developer ID Application、runtime、Timestamp）→ `check_release_identity.py`
  → `make_dmg.sh` 打 `Dayside-<版本>-<架构>.dmg` → 给 DMG 签名 → `notarytool submit --wait`（必须 Accepted，日志存档）
  → `stapler staple/validate` → `spctl` 评估 DMG 与挂载后的 app（必须 `source=Notarized Developer ID`）→ 重写 sha256。

步骤：
1. 让用户在 Xcode → Settings → Accounts 登录 Apple ID，Manage Certificates 里创建 **Developer ID Application** 证书；
   `security find-identity -v -p codesigning` 确认出现 `Developer ID Application: <名字> (<TEAMID>)`。
2. 让用户本人运行（不要替用户输入或保存密码）：
   `xcrun notarytool store-credentials dayside-notary --apple-id <Apple ID> --team-id <TEAMID>`（App 专用密码）。
3. 先 `--dry-run` 跑一遍核对计划，再两个架构各构建一次 Release（参考 `Tools/package_release.sh` 的构建命令），然后：
   `MEANTIME_SIGN_IDENTITY="Developer ID Application: …" Tools/release_sign_notarize.sh <dd-arm64>/Build/Products/Release/Dayside.app arm64`
   （x86_64 同理）。资产名由脚本按 `CFBundleShortVersionString` 生成：`Dayside-1.0-arm64.dmg`、`Dayside-1.0-x86_64.dmg`。
4. 脚本有任何一步失败：保留 `*.release-logs/`，按日志修，不要绕过检查。
5. `Tools/release_gate.sh` 和 `Tools/peak_gate.sh` 对正式签名版各跑一次，必须通过。
6. 在没装过 Dayside 的新用户账户里：从 DMG 拖进「应用程序」，双击打开，不应出现任何 Gatekeeper 警告；
   用正式签名版重做第 4 步（持久化）和第 5 步的手动 20 次。
7. 注意：`TahoeTime/TahoeTime.entitlements`（Xcode 的 `CODE_SIGN_ENTITLEMENTS`）现在与 Release 策略一致；
   工程仍关闭 Xcode 签名，正式签名一律走上面的脚本，不需要 provisioning profile（已无 App Group）。

## 11. 可选：体积账本（不阻塞发布，任何改动先问用户）

用户之前的审计（ARM64 对 ARM64）结论：Dayside.app 29.23 MB 里，城市索引 14.91 MB、主程序 11.24 MB，两者占 90%；主程序里 `__swift5_typeref` 590 KB，
有很深的 SwiftUI 具体类型组合（`TrailingWrapLayout`、`ChipFlowLayout`、`ReadingRow` 一带）。云端在 Linux x86_64 上估算 Rust 部分：链接后机器码约 3.0 MB、
静态表约 1.5 MB、展开表约 0.27 MB，合计约 4.5–5 MB（`core` 泛型实例约 0.8 MB、理解模块约 0.37 MB、serde_json 约 0.17 MB），其余约 6.5 MB 是 Swift。
1. 在 Release 构建里额外导出 Link Map（`LD_GENERATE_MAP_FILE=YES`）和匹配的 dSYM，按对象文件汇总主程序字节，写进记录。
2. 不要为体积加 `panic = "abort"`（FFI 路径依赖 `catch_unwind`）；不要改 Rust release 配置，除非 `3/s/z` × Thin/Fat LTO 的对照同时证明体积更小且 2 ms 测速门仍过。
3. SwiftUI 类型组合的拆分、城市索引的重新编码都是 1.0 之后的工作，除非用户另有指示。
